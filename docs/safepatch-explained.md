# 从零理解安全热补丁

## 模式选择与能力边界

每个 `hotpatch.targets` 可配置 `patch_mode = "cooperative"`（默认）或显式选择
`patch_mode = "compatible"`，示例见 [compatible-example.toml](../tests/safepatch/compatible-example.toml)。
严格模式失败不会自动降级。下文门禁、ABI、排空和零重叠说明均针对 cooperative。

Compatible 已有可成功安装的**受限用户态子集**。它不读取协作 ABI，不修改 RIP，
不通过杀线程完成切换。旧 RIP-only 写入路径已经删除，Cooperative、Base 保持原有行为。

### Compatible 支持条件及实际验证

当前只接受 Linux x86_64 **静态、非 PIE、单线程、无 libc 的 ET_EXEC**，使用固定
`rbp` 栈帧和直接调用。需要完整带大小的函数符号、无可执行间隙、已知 `_start`。
示例是 [restricted.c](../tests/safepatch/restricted.c)，构建命令见
[run-compat.sh](../tests/safepatch/run-compat.sh)。其中启动汇编和原始 syscall 是普通
freestanding 程序实现，不是预埋补丁协议；没有 gate、活动计数、补丁通知或协作停车点。

编译参数不是可靠性的证明。运行时另外逐项验证：

- 用 `object` 读取完整函数边界；将同一 ELF 字节快照封入 sealed memfd，由系统
  `objdump` 解码。全部可执行字节必须有明确函数归属。
- 验证每个函数的标准序言、固定栈分配和唯一标准尾声，禁止其他栈寄存器修改、
  间接调用、尾跳转及未知指令。分支只能落在本函数已解码的允许指令边界。
- 内存写指令仅允许有界的本帧局部变量写入；拒绝任意地址写、段覆盖、未知栈操作。
  当前 syscall 白名单只有 stdout/stderr `write`、`nanosleep`（剩余时间指针必须为零）
  和 `exit`；验证立即数设置与分支不能绕过设置。拒绝 clone/fork/exec、mmap、
  信号处理安装、上下文切换等调用。输出 fd 也不能是可写目标内存等特殊设备。
- 暂停后逐字核对实际可执行内存与已验证 ELF，只允许受控入口为原始字节或固定
  `mov eax,imm32; ret; nop; nop`。拒绝其他执行映射、W+X、自定义处理器和待处理信号。
- 持有 pidfd 确认原进程未退出，防止重试期间 PID 重用。用 SEIZE/INTERRUPT、带截止时间
  的 wait 确认唯一线程停止，再核对任务集合。
  启用 clone/fork/vfork/exec/exit 事件跟踪；异常事件拒绝，自动追踪到的子任务纳入
  清理。多线程目标直接拒绝。安全性依赖“完整代码验证排除线程创建”，而非两次快照
  恰好相同；本轮没有开放一般动态多线程支持。
- 对实际寄存器及每个栈帧，验证 PC 属于帧已建立且尚未拆除的指令位置、RSP/RBP
  与静态分配量严格相符、栈地址在内核标记的原生栈内、父帧严格递增且间距恰好
  等于调用者分配量加 16。每个返回地址必须对应直接 call 的下一条指令，且被调函数
  与当前帧一致。最终必须闭合到已验证的 `_start -> main`，保存 RBP 为零，并匹配
  `/proc/PID/stat` 的初始栈地址。未知帧、截断、损坏、超深栈、序言/尾声暂停均拒绝。

因此，可靠性来自受限代码的逐条约束、实际代码校验和运行时栈链闭合三者共同成立，
并非仅凭帧指针链走到零。这里不使用通用 best-effort 回溯器，也不声称提供任意 ELF 的
可靠栈服务。假设内核、objdump 及 ELF/栈内存未受外部恶意篡改，没有其他协调者或
外部写内存的参与者；不承诺对抗能伪造代码、寄存器和完整栈链的攻击者。

### 检查、重试和安装

`exchange_compat()` 自动从 ELF 获取目标**完整函数**范围。
`exchange_compat_related()` 还接受相关函数入口；Gaia 配置用
`related_functions = ["other_function"]` 声明符号，安装和恢复保留同一范围。
任一边界未知或不是函数入口都拒绝。

栈中有受影响函数时，日志记录函数、帧深度及地址，释放线程，约 2ms 后重新暂停和
检查，直到截止时间。不会因为当前 RIP 在子函数或 syscall 中就批准切换。
只有完整栈安全时，才在同一次暂停窗口读取旧字节、写入 8 字节返回值补丁、读回验证。
成功日志有 `checks>0`、`root=verified`、完整函数范围和线程数。

写入校验与操作完成分别记录。`install_verified` 时恢复状态仍是 `pending_resume`；
成功 detach 后才报告 `result=success function_consistency_complete=true`。
日志始终标记 `business_consistency=unclaimed`。函数级排空不等于异步队列、其他线程
或函数返回后业务动作排空。普通文档 demo 不符合该子集，明确拒绝，不能声称维护完成。

写入/读回失败时，在停止窗口恢复原字节并验证；detach 失败且仍可确认停止时也尝试
回滚。回滚无法完成则报告 `code_state=indeterminate` 和 `target retained stopped`，
保留 ptrace 停止供人工处理，绝不打印恢复成功或发送 SIGKILL。跟踪/恢复失败均报告
异常与未恢复状态；控制器退出可能解除内核追踪关系，因此必须在退出前处理保留的
目标。这不是崩溃后自动恢复系统。

参考 [klp_check_stack()](https://github.com/torvalds/linux/blob/master/kernel/livepatch/transition.c)、
[官方一致性模型](https://docs.kernel.org/6.15/livepatch/livepatch.html#consistency-model)
及[可靠栈要求](https://docs.kernel.org/6.9/livepatch/reliable-stacktrace.html)。
本实现没有移植完整 Linux Livepatch，未支持动态链接库、pthread、JIT、协程、信号栈、
尾调用、任意替换函数或任意长度机器码补丁；遇到这些条件拒绝，不自动退回 Base。

## 1. 我们到底在修改什么？

普通的软件升级通常是先退出程序，再启动新版本。热补丁则是在程序运行时，修改它在内存里的机器指令。

这次测试中的函数最初返回 10：

```c
int target_value(void) {
    return 10;
}
```

安装补丁后，后续调用返回 99。当前 x86_64 返回值补丁的 8 个字节表示：

```asm
mov eax, 99   ; 把整数返回值放进 eax 寄存器
ret           ; 返回调用方
nop
nop           ; 两条填充指令
```

可以把函数想象成一段正在通车的道路。修改机器码相当于施工：既要防止车辆驶入正在施工的位置，也要处理已经进入旧道路的车辆。

## 2. 两种安全问题，必须分别解决

### 2.1 写入期间，有线程还在执行这段代码

一个进程可以有多个线程。它们共享同一份函数代码，却可以在不同位置同时执行。只暂停主线程，并不代表另外 8 个工作线程也停了。

如果线程在代码修改过程中执行到被修改的位置，就可能遇到不完整或与当前执行状态不匹配的指令。

因此，第一条要求是：**写机器码时，目标进程的全部相关线程都必须已经确认暂停。** 这里采取保守做法：暂停目标进程的所有线程。

### 2.2 机器码写完了，旧调用却还没有结束

假设一个旧函数需要执行 200 ms：

```text
时间 →
线程 A：开始旧函数 ───── 等待 200 ms ───── 旧函数结束
线程 B：                安装补丁 → 开始新函数 → 结束
```

即使安装补丁时暂停了所有线程，恢复运行后，A 仍可能继续完成旧调用，B 则开始新调用。两个版本的执行时间发生了重叠。

如果两个版本对共享数据的理解不同，例如一个使用旧结构、另一个使用新结构，这种重叠就可能破坏程序状态。

所以第二条要求是：**阻止新调用进入，等现有调用全部结束，再切换代码。** 这一步称为“排空”。

只检查线程当前的指令地址也不够：线程 A 可能正在 `nanosleep()` 中，当前指令不在 `target_value()` 内，但它稍后还会返回旧函数。

## 3. 目标程序为什么必须“配合”？

当前实现采用协作式模型：目标程序主动提供入口门禁和活动调用计数。Gaia 根据这些状态协调切换，而不是尝试猜测任意线程的完整调用栈。

目标程序导出名为 `gaia_safepatch_state` 的全局变量，按顺序包含三个对齐的原子 `uint64_t`：

| 字段 | 含义 |
|---|---|
| `magic` | 固定值 `0x4741494153503031`，用于识别协议 |
| `gate` | 0 表示允许进入，1 表示暂时禁止新调用 |
| `active` | 已获准进入、但尚未完成的调用数量 |

“原子”表示读、写或加减操作不会被其他线程看到一半完成的状态。示例使用默认的顺序一致性原子操作，避免自行削弱内存顺序带来的额外问题。

这份内存布局就是这里的 ABI：目标程序和 Gaia 对字段位置、大小、含义的共同约定。`magic` 只能识别约定，不能证明所有调用方都正确遵守了约定。

### 3.1 一次调用怎样经过门禁？

下面是省略业务细节后的入口逻辑；完整版本见 [target.h](../tests/safepatch/target.h)：

```c
for (;;) {
    while (atomic_load(&state.gate)) {
        sched_yield();  // 暂时让出 CPU，等门重新打开
    }

    atomic_fetch_add(&state.active, 1);

    if (atomic_load(&state.gate)) {
        atomic_fetch_sub(&state.active, 1);
        continue;       // 加入期间门关了，退出计数后重试
    }

    int value = target_value();
    // 完成仍然依赖该版本的后续操作……
    atomic_fetch_sub(&state.active, 1);
    break;
}
```

计数和门禁必须位于会被覆盖的函数入口之外。否则补丁直接执行 `ret`，就可能跳过原来的计数或清理代码。

### 3.2 为什么要检查两次 gate？

考虑下面的顺序：

1. 工作线程第一次看到门是开的。
2. Gaia 关闭门。
3. 工作线程才增加活动计数。

第二次检查可以发现门已经关闭，让线程撤销计数并重试。它不能凭第一次检查的结果继续进入函数。

另外，`active` 必须覆盖完整的受保护执行区间。函数返回后如果还有操作依赖旧版本数据，也应把这些操作放在减计数之前。

## 4. Gaia 实际怎样完成一次切换？

核心代码是 [safepatch.rs](../gaia-xdp/src/safepatch.rs) 中的 `exchange()`。它接收进程号、协议变量地址、补丁地址、待写入字节和排空超时时间，成功时返回修改前的原始字节。

### 第一步：找到全部线程，逐个确认暂停

Linux 的 `/proc/<PID>/task/` 目录列出进程的线程。`Stopped::all()` 读取这些线程号，然后对每个线程：

1. 用 `PTRACE_SEIZE` 建立追踪关系。
2. 用 `PTRACE_INTERRUPT` 请求暂停。
3. 用 `waitpid(..., __WALL)` 等待，并检查实际停止状态。

`ptrace` 是 Linux 提供的进程追踪接口，调试器也会使用它。请求暂停和已经暂停是两回事，因此必须等待确认。

全部线程停下后，再读取一次线程列表。如果前后不一致，就拒绝继续。这是对固定线程模型的检查，不代表支持任意动态创建、退出线程的程序。

### 第二步：验证协议，关闭入口

Gaia 检查 `magic`，并确认门当前没有被其他协调者占用。然后，在所有线程暂停的状态下，把 `gate` 写为 1。

此时还没有修改函数代码。

### 第三步：检查是否还有旧调用

如果 `active == 0`，说明协议覆盖的旧调用已经完成，可以进入写入阶段。

如果 `active > 0`，Gaia 会：

1. 保持门关闭，解除线程暂停。
2. 让已有调用继续执行，新调用在门口等待。
3. 等待约 2 ms 后，再次暂停全部线程。
4. 再次检查活动计数。

为什么要恢复线程？因为暂停中的旧函数无法完成；一直暂停并等待计数变成 0，会让排空无法推进。

这里的 2 ms 是重试间隔，不是安全判据。真正的判据始终是：**全部线程已暂停，并且活动计数为 0。**

### 第四步：保存旧代码，写入并读回

只有达到安全条件后才会：

1. 用 `PTRACE_PEEKTEXT` 读取原始字节。
2. 用 `PTRACE_POKETEXT` 按 8 字节机器字写入补丁。
3. 再读取目标内存，逐字节比较实际内容与预期内容。

因此，“写入调用没有报错”还不够，必须通过读回校验。分多次写入也不依赖单次写入是否原子，因为此时所有线程都停止了。

运行时记录 `switch_ns`，它是写入校验后、重新开放入口前取得的单调时钟时间戳，可用于与测试调用区间对照。

### 第五步：重新开放入口，恢复线程

Gaia 把 `gate` 改回 0，再解除追踪。后续调用就会执行新代码。

恢复原始机器码也调用同一个 `exchange()`：先排空当前版本，再切回原始版本。恢复不是可以省略安全检查的例外。

## 5. 出错时怎样处理？

| 情况 | 当前处理 |
|---|---|
| 不支持的架构、无协议变量或门已被占用 | 拒绝写入 |
| 线程没有按预期暂停、线程集变化 | 中止本次操作 |
| 排空等待超过限制 | 常规路径下重新开门，保留原代码，返回错误 |
| 写入失败或读回不一致 | 在线程暂停期间写回本次修改前的字节 |
| 机器码回滚也失败 | 发送 `SIGKILL`，避免目标继续执行部分修改的指令 |
| 写完后释放门禁失败 | 尝试回滚机器码，返回错误 |
| 恢复原始代码失败 | Gaia 保留已保存的字节，供后续重试 |

Gaia 调用路径使用 5 秒排空超时。不过，这不是所有系统调用的总耗时上限；例如等待线程进入停止状态使用的是阻塞式等待。

也不能把所有异常都理解成“自动恢复正常”。重新附着线程失败时，门禁可能保持关闭，需要人工处理；解除追踪失败会记录错误。当前实现没有覆盖所有极端故障的自动恢复。

## 6. eBPF 在其中起什么作用？

Aya 是项目使用的 Rust eBPF 框架。这里通过 Uprobe 观察用户态函数入口，通过 Uretprobe 观察函数返回。

可以把它们理解为入口和出口的观察点。每个线程的观测状态存入 `SAFEPATCH_CALLS`：

- 键包含完整 TGID/TID。TGID 通常对应进程号，TID 标识具体线程。
- 值包含调用嵌套深度，以及最近一次入口的单调时钟时间。
- 进入时深度加一，返回时减一，多个被探测函数共享该线程的嵌套统计。

更新失败或出现没有匹配入口的返回时，会增加 `SAFEPATCH_OBSERVATION_ERRORS`。该计数使用每 CPU 独立存储，查询接口汇总各 CPU 的值。

运行中 Gaia 的 `GET /api/v1/hotpatch-observation` 暴露这些快照，并标注 `advisory_only: true`。

**这些数据用于辅助观察，不负责批准代码写入。** 如果探针附着得太晚，旧调用可能没有入口记录；异常退出可能没有返回记录；映射表和事件传输也有容量限制。因此，“没有观测到活动调用”不能推导为“没有活动调用”。错误计数也无法发现所有漏记。

真正的写入条件仍由协作计数和全线程暂停共同提供。Uprobe 附着成功只说明观测点建立成功，不说明补丁字节已写入。

## 7. 怎样接入 Gaia 和 reload 接口？

[main.rs](../gaia-xdp/src/main.rs) 中的 `ptrace_read_and_write()` 现在先从目标可执行文件解析 `gaia_safepatch_state` 的运行时地址，再调用安全协调器。成功后保存进程号、函数地址和原始字节。

`code_patches` 互斥锁把 Gaia 自身的代码切换请求串行执行，避免两个请求同时修改同一份补丁状态。协议仍要求没有外部竞争协调者。

`POST /api/v1/reload-hotpatch` 的执行顺序是：

1. 附着观测探针，更新相关 BPF 配置。
2. 恢复此前的代码补丁；如果仍有恢复失败的记录，返回失败。
3. 安装当前配置中启用的代码补丁。
4. 比较实际成功记录数和请求安装数，不一致则返回 `success: false`。

监控模式不需要修改机器码，因此不计入代码补丁数量。其他配置增删改接口仍返回配置列表，不能用它们的配置响应代替补丁执行结果。

当前也没有实现“多个目标要么全部成功，要么全部撤销”的事务。例如第一个目标成功、第二个失败时，reload 会报告失败，但第一个补丁可能已经生效。

## 8. 使用范围和代价

当前实现要求：

- Linux x86_64，固定线程集；测试程序为非 PIE，并禁止内联。
- 所有进入受影响函数的路径都遵守门禁和计数约定，当前版本也一样。
- 不通过未纳入协议的递归、信号处理函数或其他入口调用目标函数。
- 不使用绕过正常减计数的非局部跳转等退出方式。
- 不在协调期间创建或销毁线程、fork/exec、自行修改代码或使用 JIT。
- 没有其他调试器或补丁协调器竞争修改目标状态。

程序目前使用一个进程级活动计数，可能连带等待其他受保护函数，选择的是保守排空。

原有远程 `dlopen` 注入路径尚未满足这套协议，因此 `replace_function` 会被拒绝；不能因为存在旧的注入辅助代码就认为它受安全协调器保护。当前测试覆盖的是入口返回值补丁及其恢复。

安全性也有代价：每次调用要增加原子操作，切换时要暂停多个线程，长调用需要等待完成。它缩小了允许修改代码的时机，并没有消除这些成本。
