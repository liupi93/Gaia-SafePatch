# 运行测试与解读结果

本页介绍已经提供的自动化实验。先读[原理说明](safepatch-explained.md)，再运行实验，会更容易理解各项检查的意义。

## 1. 准备环境

在 openEuler x86_64 上准备：

- C 编译器 `cc`，以及 pthread 开发环境。
- 可用的 Rust/Cargo 工具链及依赖；首次构建可能需要下载依赖。
- Python 3、Git。
- 允许测试驱动追踪其子进程的运行环境。容器或沙箱可能额外限制 `ptrace`。

测试程序通过 `PR_SET_PTRACER` 允许父进程驱动进行追踪，但这不能绕过容器或沙箱的限制。遇到权限错误，应先确认运行环境的追踪权限。

还需要原版 `base` 分支。当前实验已经按约定将原版提交保存为：

```text
base = eec1660a4d6679fb3ce687b757a25578a6abd326
```

可以先检查：

```bash
git rev-parse base
```

如果在其他检出环境中不存在这个分支，应先定位正确的原版提交，再创建 `base`。不要随意把已经包含安全修改的新提交当作原版。

测试驱动的 `build.rs` 会从 `base:gaia-xdp/src/main.rs` 提取原版 `ptrace_read_and_write()`，直接编译进驱动用于对照。这样比较的是实际原版写入函数。它不需要把当前开发工作区切回原版。

## 2. 一条命令运行实验

在仓库根目录执行：

```bash
bash tests/safepatch/run.sh /tmp/gaia-safepatch-results
```

脚本依次执行：

1. 编译高频调用、长调用和性能对照用的 C 程序。
2. 构建 Rust 驱动；它直接引用 Gaia 使用的 `safepatch.rs`。
3. 对两个安全测试分别执行 20 次安装和 20 次恢复。
4. 在长调用测试中验证排空超时，检查无效地址与无效 ABI 被拒绝。
5. 用原版写入器运行可控的新旧调用重叠实验。
6. 交替运行 3 组 base/safe 性能采样。
7. 分析调用日志，打印结果并写入 `results.json`。

每个目标包含 8 个工作线程，加上主线程，一共应暂停 **9 个线程**。驱动正常结束和返回错误时都会尝试终止并回收它启动的目标进程。脚本使用 `set -e`，某一步失败会中止，不会把失败阶段补成成功结果。

原版实验故意执行不安全写入，目标有可能崩溃。这属于真实实验失败，应保留日志分析；本脚本不保证原版一定存活，也不要求一定崩溃。

## 3. 两个安全测试分别验证什么？

### 测试 A：高频调用

8 个工作线程不停调用 `target_value()`。原始函数返回 10，入口代码被覆盖后返回 99。

驱动在并发调用期间反复安装和恢复。目标程序如果读到其他返回值，会报错并中止。这个测试用来给暂停、代码写入和恢复制造高频并发压力。

### 测试 B：长调用

原始 `target_value()` 内部有约 200 ms 的等待，补丁版本直接返回 99。

工作线程通过启动屏障共同开始。驱动读取实际活动计数，等至少有一个调用进入后，尝试一次零排空超时的切换，要求它失败。这里不是仅靠“先睡一会儿”来猜测旧调用正在执行。

随后进行正常的反复切换。每次完成的调用都会记录：

```text
CALL 线程编号 开始时间ns 结束时间ns 返回值
```

例如下面是一条说明格式的示意，**不是实测输出**：

```text
CALL 0 1000000000 1200000000 10
```

它表示工作线程 0 的旧版本调用从 1.0 秒持续到 1.2 秒。这里的线程编号是测试分配的 0～7 编号，不是 Linux TID。

分析器将已完成调用按开始时间排序，检查不同版本的时间区间是否重叠。同时检查调用是否跨过运行时记录的机器码切换时间。时间都使用单调时钟，适合比较持续时间和事件先后顺序。

区间分析依赖已完成并记录的调用。测试最后直接终止目标，尚未完成的调用不在这个统计里；测试通过不等于验证了任意程序、任意退出方式的全部行为。

## 4. 怎样可控地证明原版的风险？

风险实验按下面的顺序执行：

1. 暂时把 7 个工作线程挡在一个独立的测试控制点。
2. 让剩下的 1 个线程进入旧版长函数，并读到活动计数大于 0。
3. 用原版单线程暂停写入器安装补丁。
4. 释放另外 7 个线程，让它们进入新函数。
5. 收集日志，要求实际出现新旧版本调用区间重叠。

这提供了一个可检查的执行交错，而不是依赖偶发崩溃。若本次调度没有形成可观察的重叠，分析断言会失败，不会自动宣称风险已经实测复现。

`base_risk_overlapping_intervals` 统计的是遇到另一版本活动区间的调用数量，不是“同时运行的线程数”，也不是所有重叠调用对的数量。新版本返回得很快，一次实验也可能产生大量被统计的调用。

这部分日志与安全模式日志分开；原版故意制造的重叠不计入安全模式的零重叠指标。

## 5. 去哪里找日志？

输出目录默认是 `/tmp/gaia-safepatch-results`：

| 文件 | 内容 |
|---|---|
| `high_frequency.summary`、`long_running.summary` | 成功切换数、耗时、调用数等摘要 |
| `*.runtime` | 运行时校验、暂停线程数、活动计数、切换时间和错误 |
| `long_running.calls` | 长调用测试的已完成调用区间 |
| `base-risk.calls`、`base-risk.summary` | 原版风险实验的区间与活动计数 |
| `perf-base-*.summary`、`perf-safe-*.summary` | 三组性能采样 |
| `base-commit` | 原版分支提交号 |
| `results.json` | 分析后汇总结果 |

例如：

```bash
cat /tmp/gaia-safepatch-results/results.json
cat /tmp/gaia-safepatch-results/long_running.summary
```

运行时成功写入日志包含：

```text
SafePatch write verified pid=... threads=9 active=0 switch_ns=... drain_us=...
```

`threads=9` 表示本轮暂停了主线程和 8 个工作线程，`active=0` 表示检查时受保护调用已经排空。分析器会检查这两个条件。

这里的 `drain_us` 从 `exchange()` 开始计时，包含暂停、重试以及成功写入校验的开销；它不是单纯旧函数剩余执行时间。摘要里的排空均值和最大值收集的是**安装操作**，没有把恢复耗时混入该均值。

## 6. 已记录的实际结果

[measured-results.json](../tests/safepatch/measured-results.json) 保存了 2026-11-06 的一次真实运行结果。环境是 openEuler 24.03 SP4 x86_64，内核为 `6.6.0-159.4.19.173.oe2403sp4`。

| 指标 | 结果 |
|---|---:|
| 安装成功次数 | 40 |
| 恢复成功次数 | 40 |
| 已校验的安全模式机器码写入次数 | 80 |
| 安全模式不安全写入次数 | 0 |
| 安全模式新旧区间重叠次数 | 0 |
| 跨越切换时间的已完成调用数 | 0 |
| 机器码恢复失败次数 | 0 |
| 高频安装耗时均值 / 最大值 | 19.889 / 29.155 ms |
| 长调用安装耗时均值 / 最大值 | 177.461 / 200.935 ms |
| 原版风险实验中重叠的调用数 | 338972 |
| 安全模式性能吞吐下降 | 约 13.28% |

为什么有 40 次安装？因为两个安全测试各安装 20 次。为什么有 80 次写入？因为恢复原始代码也要写一次。性能采样中另行进行的切换不计入这里的 80 次。

这些数字属于这次记录，重新运行时数值会变化；不要把该文件当成任何新环境的实测结果。

### 性能下降是怎样计算的？

两种模式都进行 20 轮安装和恢复，每次安装、恢复后分别保持约 25 ms。base 程序去掉协作门禁和活动计数操作，safe 程序保留它们；两者都保留调用计时和总调用计数。

各取 3 次调用吞吐量的中位数：

```text
base：约 3053 万次/秒
safe：约 2647 万次/秒
吞吐下降百分比 = (1 - safe吞吐 / base吞吐) × 100%
```

这测量的是**原版写入器与安全运行时、协作协议的微基准差异**。测试代码使用 `-O0`，没有绑定 CPU，结果受调度和测量代码影响。它不等于整个 Gaia 守护进程或加载 eBPF 后的性能开销，也不适合直接预测数据库等真实服务的吞吐变化。

## 7. 哪些验证已经做了，哪些还没有？

已完成的记录包括真实 C 目标进程、真实 ptrace 暂停与写入、读回校验、反复恢复、超时与错误输入、原版受控风险交错，以及微基准性能采样。

完整编译检查也已通过，包含实际 BPF 目标构建：

```bash
cargo check --offline -p gaia-xdp
```

但上面的一键运行时套件**不会启动 Gaia HTTP 服务，也不会加载 BPF 对象**。因此，以下项目不能从这次结果推导出来：

- 内核 BPF verifier 已经接受并加载了这些程序。
- 运行中的观测接口已经正确采集到目标线程的完整调用历史。
- 对真实运行的 Gaia 调用 reload 接口已经完成端到端验证。

编译通过、运行时测试通过、BPF 加载通过和 HTTP 集成通过，是不同层次的证据。

## 8. 遇到错误先看哪里？

| 现象 | 检查方向 |
|---|---|
| 找不到 `base` 或原版函数 | 确认分支存在，且指向原版提交 |
| `Operation not permitted` | 检查 ptrace 权限及容器、沙箱限制 |
| Rust 工具链或依赖错误 | 先确认工具链可用；构建完整 Gaia 还需要项目要求的 WebUI/BPF 构建工具 |
| 缺少协作 ABI | 目标是否导出了正确变量，是否使用了正确可执行文件和地址 |
| 排空超时 | 查看是否有调用未返回、调用路径漏减计数，或预设超时太短 |
| `thread set changed` | 目标违反固定线程集模型，应先修改目标的线程生命周期 |
| 写入或恢复失败 | 保留 runtime 日志，检查目标存活、地址有效性和权限；不能只看探针是否附着 |
| 原版风险分析断言失败 | 检查目标是否崩溃、区间是否完整、实际交错是否形成，不要手动改结果为通过 |

更多协议约束和异常行为见[实现原理](safepatch-explained.md)。

## 9. 非协作兼容模式与三模式对照

```bash
# 使用已有工具链可避免 rust-toolchain.toml 自动更新；也可移除该环境变量使用 nightly。
bash tests/safepatch/run-compat.sh /tmp/gaia-safepatch-compatible
bash tests/safepatch/run.sh /tmp/gaia-safepatch-three-modes
```

兼容脚本编译 `compatible.c`：8 个工作线程与主线程，不导出协作 ABI，也不执行门禁
或活动计数。普通调用间有短暂休眠以提供可重复的无冲突窗口；另一个场景让全部工作线程
持续在覆盖区间内循环，必须重试并超时，目标继续存活。普通场景完成 20 次安装和恢复，
检查原始字节与补丁字节，验证缺失 ABI 的严格模式、无效地址、溢出、空/非整字长度均失败。
脚本断言 40 条校验日志均为 `threads=9 rip_clear=true`。

同一脚本还运行仅在 `cfg(test)` 编译的真实 ptrace 故障注入：16 字节写入中第二个机器字
失败或注入一次读回不一致，要求回滚读回等于原始内容；持续失败则要求目标被终止并回收，错误不能变成成功。
注入钩子不会编译进 Gaia 运行程序。测试没有覆盖所有信号交错、线程变化、GETREGS/DETACH
失败或内核异常；日志中的线程数来自已确认停止的集合，不能替代这些故障场景的专项验证。

原有 run.sh 保留 cooperative 零重叠断言，并增加 `compat-risk` 受控长调用实验。
该实验沿用原版风险实验的控制点与计数器，仅用于确定测试交错；兼容写入器不读取它们。
分析器分别要求 base 与 compatible 出现实际新旧调用区间重叠；compatible 的两次切换仍
必须满足 9 个线程停止和 RIP 无冲突。这样对比安全保证，而不把兼容模式误标成排空模式。
`results.json` 增加 `compatible_risk_overlapping_intervals`。兼容独立套件证明无需 ABI，
受控风险实验则用测试设施证明其局限，两者目的不同。

完整守护进程检查与运行套件分开：nightly/BPF 工具链不可用时应如实记录阻塞。
使用 `AYA_BUILD_SKIP=1` 且复用已有 BPF 对象只能证明用户态编译，不能声称重新构建或加载 BPF。

本次机器实测保存于 [measured-compatible-results.json](../tests/safepatch/measured-compatible-results.json)：
协作模式 40 次安装、40 次恢复、80 次校验写入，零新旧区间重叠；独立无 ABI 兼容目标
20 次安装、20 次恢复、40 次校验写入。受控风险实验 base 重叠计数 107061、compatible
90610，表明兼容模式没有排空保证；这些计数不是性能比较。部分写失败、读回不一致回滚、
持续回滚失败后的终止回收均通过。用户态编译通过，完整 BPF 重建受 nightly 工具链故障阻塞。

调试中早期版本的致命回滚测试曾等待追踪线程退出而阻塞；现已修复为先终止并逐线程回收，
最终测试通过。该轮遗留的 root 所有测试进程（38062、38171，及其退出中的子进程）
无法由当前用户清理，普通 kill 被拒绝且 sudo 需要密码；需由进程所有者处理。
