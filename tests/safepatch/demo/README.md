# 录屏 Demo：代码安全与业务切换是两道边界

限定 Linux x86_64。使用真实子进程、8 个工作线程和 1 个主线程、真实 ptrace。
驱动直接引用当前 safepatch.rs；base 则由现有 build.rs 从 `base` 分支提取原版函数，
不改变原版暂停与写入算法。这里**没有启动 Gaia HTTP 服务或加载 eBPF**，录屏应称为
“Gaia 原版写入器 / SafePatch 运行时演示”，不能称为 Gaia WebUI 端到端验证。

## 准备

从仓库根目录运行：

```bash
bash tests/safepatch/demo/run.sh
python3 tests/safepatch/demo/repeat.py
```

前一命令构建两个目标、运行全部五幕并保存每幕日志；后一命令自动重复验证 55 个场景。
需要 `base` 分支指向原始提交、cc、objdump、Cargo 依赖以及追踪子进程权限。
默认产物与日志位于 `/tmp/gaia-video-demo`。目标禁用 core dump，以免故意崩溃生成大文件。
普通目标 `plain` 不导出 gaia_safepatch_state；协作目标仅通过 `-DCOOPERATIVE` 增加协议。
可通过 `nm /tmp/gaia-video-demo/plain | rg gaia_safepatch_state` 确认无该符号。

## 第一幕：原版恢复到了新指令的中间（约 1 分钟）

先显示源码中 entry_policy 和反汇编：

```bash
objdump -d --disassemble=entry_policy /tmp/gaia-video-demo/plain
bash tests/safepatch/demo/show.sh entry base
```

讲解画面：

```text
旧入口：31 c0 | eb fe | 90 90 90 90
        eax=0  跳回自身
                ↑ 工作线程 RIP 始终停在 +2

新入口：b8 63 00 00 00 | c3 | 90 90
        eax=99          ret
              ↑ 从 +2 继续解码，得到 00 00，即 add byte ptr [rax], al
```

旧代码只是人为延长入口执行时间的有效循环，本身不会访问非法内存。驱动读取实际
线程寄存器，确认 RIP=entry+2，然后解除追踪；**不修改寄存器、不拆分写入、不伪造信号**。
原版只暂停主线程，写入完整 8 字节后，工作线程从 +2 执行新字节，RAX 原本为 0，
访问地址 0，实际收到 SIGSEGV。驱动检查真实退出信号，缺少崩溃就测试失败。

这是特制的、可重复的指令交错反例，不代表普通函数每次都会崩溃。
讲解重点：“即使一次写完 8 字节，线程也可能从新代码中间继续执行。”

## 第二幕：相同程序与补丁，兼容路径拒绝危险切换（约 1 分钟）

```bash
bash tests/safepatch/demo/show.sh entry compatible
```

工作线程仍在 +2，400 ms 后 RIP conflict timeout。驱动断言：错误类型正确、进程仍存活、
原始 8 字节没有改变。演示结束由驱动主动清理目标，因此“存活”是指拒绝后、清理前。

讲解：“这里正确的结果就是拒绝补丁。目标没有提供协作 ABI，Gaia 仍能避免这次危险写入。”

## 第三幕：基线业务结果混用（约 1 分钟）

```bash
bash tests/safepatch/demo/show.sh orders base
```

折扣策略原版返回 10，但耗时约 1.2 秒。一个旧订单先进入；另外七个订单等待测试释放。
旧订单已经进入后才安装返回 99 的补丁，随后释放新订单。

预期：七个 99 先提交，最后旧订单 10 标记为 “旧结果迟到”。
业务要求是“新策略结果开始提交后，不再提交旧策略结果”；这种要求下存在切换一致性问题。
程序使用原子指标，不依赖 C 数据竞争或故意 abort 来制造业务错误。

## 第四幕：兼容路径写入正确，但旧结果仍迟到（约 1 分钟）

```bash
bash tests/safepatch/demo/show.sh orders compatible
```

与第三幕使用同一个 plain 文件。旧订单此刻在等待函数中，RIP 不在入口。
因此全部 9 个线程停止、RIP 检查通过、写入并读回成功，仍会出现 “旧结果迟到”。
入口包含 8 个 NOP，避免把这一幕的业务交错与第一幕的指令风险混在一起。

讲解：“线程现在不在入口，不代表旧函数已经执行完。兼容模式没有承诺排空。”
安装后驱动检查真实补丁字节，订单全部完成后调用同一模式恢复，再检查恢复内容。

## 第五幕：只加协议，保护完整业务区间（约 2 分钟）

先展示 target.c 中 `#ifdef COOPERATIVE` 的少量变化：协议状态、enter 双重门禁检查、
以及**提交日志之后**才减少 active 的代码。然后运行：

```bash
bash tests/safepatch/demo/show.sh orders cooperative
```

预期顺序：

```text
旧订单进入 → 发起补丁 → 旧订单 10 提交
→ active=0、写入校验 → 七个新订单 99 提交 → 安全恢复
```

补丁安装需要约 1.2 秒，而兼容路径通常很快；这额外等待换来了排空保证。
输出必须为 “8 个订单全部完成；迟到的旧结果：0 个”，否则测试失败。协作式没有宣称更低切换延迟。

测试释放标志、old_started 和统计只用于确定演示交错；兼容运行时不读取这些状态。
所有工作线程完成订单后仍保留，直到演示结束，维持固定线程集合。

## 结果判读

| 场景 | 原版 | compatible | cooperative |
|---|---|---|---|
| 入口 +2 持续执行 | 实际 SIGSEGV | 超时拒绝、代码不变、目标存活 | 此幕不测试；永不结束的受保护调用也无法排空 |
| 旧订单在途时安装 | late_old=1 | 全线程停止且校验成功，但 late_old=1 | 等待旧订单提交，late_old=0 |
| 安装与恢复 | 字节检查 | 同模式安全流程与字节检查 | 同模式排空流程与字节检查 |

视频中不要把这两个特定场景的通过率推广成任意目标的安全保证，也不要把人为等待时长当作性能基准。
没有 HTTP、BPF 加载、动态线程、任意异常信号和真实业务部署的覆盖。

本机重复实测：[measured-results.json](measured-results.json)，共 55 次断言通过（另有首轮五幕运行）。示例输出保存在同目录 example-*.log；这些是记录，不代替重新运行。

## 中文录屏界面

所有演示命令使用仓库 `rust-toolchain.toml` 配置的 nightly，不依赖 stable。
`show.sh` 将底层校验日志解释为中文；未知错误仍原样输出，并保留失败退出码。
编译器诊断保存在产物目录 `build.log`，构建失败时显示原始诊断，便于排查。
视频建议先运行 run.sh 完成准备，正式录制时逐幕运行 show.sh，避免展示编译过程。

术语可这样讲：线程是“程序里同时工作的工人”；机器码是“处理器实际执行的指令”；
RIP 是“线程接下来要执行的位置”；排空是“先拦住新任务，等已经开始的任务做完”。
原版入口幕中的“检查通过”指成功复现了异常，不代表补丁操作安全。
